# Risk assessment module — design for sign-off

Draft v0.1 · 12 Nov 2026 · Status: **waiting for sign-off. Nothing is built yet.**

Paths: `BE` = `company-brain-backend/scraper`, `FE` = `company-brain-app/src`.

---

## 1. What exists today, and where risk fits

### 1.1 Data and graph

- **Graph storage**
  - Nodes are `company_entities` (domain = people / processes / systems / data / policies / controls / risks / evidence / overview), with free-text `attrs` JSON.
  - Edges are `entity_relationships` (`governed_by`, `implements`, `mitigates`, `proves`, `owns`, …).
  - The cascade reads a separate JSON copy, `cascade_graph`, that `cascade_sync` rebuilds.
- **Compliance chain**
  - regulations → sections / obligations → `requirements` → company requirement instances (CRI) → `company_requirement_scopes`.
  - The applicability engine sets regulation-level verdicts. `req-engine/1` sets the requirement-level ones.
  - `gap_assessments` hold MET / PARTIAL / GAP / NOT_COVERED, plus gap, fix and covered_by.
  - `controls`, `control_requirements`, `evidence` (valid_from / valid_until, verification_status), `evidence_links`, `compliance_tests`, `findings`, `actions` (CAPA lifecycle, with `action_events`).
- **Risk today**
  - There is no risk table. A risk is a `company_entities` row with domain = risks, and five things write them: the client's xlsx register, the same xlsx re-parsed by cascade_sync, five hard-coded "measured" risks, LLM remediation drafts, and connector rows.
  - Cascade risk nodes come **only** from the xlsx, reached through control codes.
  - The per-requirement `rk` (Critical/High/…) is a **priority band**, not a risk. For NABH it comes from a rule (category × status). For every other regulation it is the LLM's own severity.
- **History.** There are no inspection, observation, incident, recall, complaint or litigation records. The only exceptions: `findings` are generated by the system itself, and connector-imported inspections and complaints are filed as evidence.
- **Versioning.** gap rows, CRI status, `impact_scores` and `cascade_graph` are all overwritten in place. Only `action_events`, `obligation_events`, the flat `audit_events` log and regulation `document_versions` / `section_changes` keep history.

### 1.2 Scoring precedents

| Engine | Kind | Reuse for risk |
|---|---|---|
| `applicability.py` (weights, gates, `_confidence`, missing_facts, engine_version) | Rules, no model | **The template**: gates, a confidence that is separate from the verdict, missing facts listed, a version on every result |
| `penalties.py` (regex, verbatim basis_text) | Rules | Seeds **regulatory impact** |
| `impact_v2.py` (exposure × severity × likelihood × reach; residual = inherent × (1 − 0.6 × coverage)) | Rules | Shows the shape we want. But **likelihood is a constant 0.8**, and three writers set `regulations.impact_score` with three formulas. The risk module will not read `impact_score`. |
| `enforcement.py` (RBI penalty press releases) | Rules | Not linked to any regulation yet. Becomes a reputational / likelihood signal once it is linked. |
| `nabh6_gap.py` category → band | Rules | NABH category becomes an **impact floor** in the healthcare pack |
| Gap review (`st`), non-NABH `rk` | **LLM** | `st` is used only as a capped control signal, marked unconfirmed (see §2.4). `rk` is **not used**. |

### 1.3 Intake

- **Company profile**
  - Company Setup writes one `company_profile` row: entity type, sectors, licences (chips only), 9 jurisdiction chips, employees, turnover and patients a year.
  - `beds` exists as a column but is never collected or persisted.
  - The setup code always writes jurisdictions as `["India"]`.
- **Spreadsheet import.** 12 sections, stored as `company_entities.attrs` free text:
  - locations
  - licences with number and valid-till
  - controls with last-tested
  - risks with inherent, residual and appetite yes/no
  - …and the rest
- **Document intake**
  - It extracts type, code, version, dates, owner and approver, with a 600-character excerpt.
  - It records **no page numbers**, and the gap review cites only document codes, never quotes.
  - Confirm and correct exist per document, and for the profile as a whole.
- **LLM.** Local `gpt-oss-120b` first, with a fallback chain. Guardrails already in place: JSON-only replies, cited codes checked against real documents, and "no key, no answer".

### 1.4 Human review

- **Roles:** viewer < reviewer (propose) < compliance_manager (approve) < admin, plus auditor. There is no leadership or board role.
- **Patterns worth reusing:**
  - the actions lifecycle (409 on an illegal move, a closure note, `action_events`)
  - the obligation lifecycle, which requires a reason (no screen uses it)
  - Governance's dry-run → apply preview
  - the Auditor approve/decline form with a note
  - the impact-agent confidence floor that interrupts the run
- **Missing:**
  - risk appetite
  - review tasks with an assignee and a due date
  - overrides with a reason
  - versioned decisions
  - routed review screens (ActionsPage, ReviewQueuePage and ImpactEnginePage are all unrouted)

### 1.5 Screens

- `/risks` is the generic entity list: inherent and residual badges, category, owner, status.
- `HeatGrid` exists in charts.tsx but is unused.
- `ImpactPanelTab` (inherent, residual, formula, drivers) is the precedent for the derivation panel.
- Panels to reuse: `SidePanel` / `EntityDrawer`, `PeoplePicker`, `DiffView`, `ActivityList`.

### 1.6 Defects that matter for this module (fix in Phase 0 or along the way)

1. `materialise_cri` deletes and rebuilds CRIs, and `findings` / `compliance_tests` are `ON DELETE CASCADE`. **Risk tables must key on (regulation_id, requirement_id), never cascade from CRI.** *(Blocker)*
2. `beds` is not persisted, and jurisdictions are hard-coded to `["India"]`. Both are exposure and applicability inputs. *(Blocker)*
3. New tables must join `tenancy.COMPANY_TABLES`. `company_id=1` is hard-coded in several places. *(Blocker)*
4. `api_cascade` filters `status <> 'NOT_APPLICABLE'` on the raw table, so the NOT_ASSESSED rows from migration 004 drop out of the cascade.
5. `api_regulation_tabs` joins risks to controls by owner_id, and shows unrelated risks when nothing matches.
6. Notification links to `/actions` are dead, because the route redirects.

## 2. Where I'd change the brief

1. **"Every APPLICABLE obligation generates a risk" would produce about 17,000 risks.** There are about 3.4k checked requirements and 13.7k not yet assessed.
   - ISO 31000 risks are events, not clauses. So I keep the obligation as the **scoring atom** (an "exposure"), and group exposures into **risks by (theme, site)**. A hospital ends up with roughly 100–300 risks.
   - The grouping is explicit and comes from rulebook data (§4.1).
2. **APPLICABLE-only is too narrow.** Today 470 of the 650 regulations that apply are CONDITIONAL, because thresholds are not extracted.
   - CONDITIONAL becomes a candidate risk with a confidence penalty.
   - An applicability of REVIEW_REQUIRED gives the verdict REVIEW_REQUIRED (gate 3).
3. **Impact × Likelihood as a product, with band thresholds, is a known flaw.** A rare catastrophe (5×1 = 5) would rank with a frequent trivial issue (1×5).
   - I keep the 5×5 scale, but the band comes from a **lookup matrix in the rulebook**. Safety-catastrophic rows can then never fall below HIGH.
   - The product is stored too, for sorting only.
4. **"The LLM never assigns a score" is not true today.** Gap status (`st`) and non-NABH `rk` are LLM judgements.
   - `rk` is not used at all.
   - `st` is treated as a **proposed fact**: it caps control effectiveness and carries a confidence penalty until a person confirms it.
   - Regulatory impact comes from penalty and licensing rules instead.
5. **Delegated legislation rarely states its own penalty.** For example, the Bio-Medical Waste Rules are punished under the Environment (Protection) Act.
   - We use `regulations.enabling_act` to inherit the parent Act's penalty provisions.
   - Licensing consequences ("suspend / cancel registration") need a new regex extractor, alongside `penalties.py`.
6. **"Absence of history" must be split into two cases:** "no records collected" versus "client attests none in 36 months".
   - Without an attestation, likelihood cannot be scored, and the verdict is INSUFFICIENT_EVIDENCE.
   - On day 1, most risks will therefore be INSUFFICIENT_EVIDENCE. That is by design, and the gap list shows the three or four inputs that unlock most of them.
7. **Control status UNKNOWN is not the same as ABSENT.** ABSENT means "confirmed: nothing there", and residual = inherent. UNKNOWN means "we don't know yet", and the verdict is INSUFFICIENT_EVIDENCE.
8. **A risk owner must not accept a risk above tolerance alone** (COSO). Accepting a risk whose verdict is ESCALATE needs a leadership decision.
9. **"All sectors" cannot be calibrated at once.**
   - v1 ships the base rulebook plus a calibrated **healthcare** pack, because the demo corpus is a hospital.
   - The pharma, food, finance, manufacturing and data packs ship as **stubs flagged uncalibrated**. This costs a confidence penalty, and the flag shows on screen.
10. **Change velocity raises likelihood only for the duties that changed**, inside a transition window, and only while the company's evidence predates the change. It does not apply to the whole regulation forever.

## 3. Framework mapping (what each one contributes, not its taxonomy)

| Framework | Where it plugs in |
|---|---|
| **ISO 31000** (process spine) | The steps map onto the module like this: context (profile + appetite) → identify (obligation exposures, grouped into risks) → analyse (rulebook) → evaluate (against appetite) → treat (owner decision + actions) → monitor & review (ripple recompute, review cadence, bitemporal history). The HITL gates cover consultation; the board view covers reporting. |
| **COSO ERM** | Governance only: who sets appetite and tolerance (leadership), the tolerance-breach → ESCALATE rule, the portfolio / board view, and movement since the last assessment. |
| **NABH** (healthcare pack) | Theme mapping by chapter (HIC → infection control, MOM → medication, FMS → facility safety, …). The category (CORE / COMMITMENT / …) sets an impact floor. The register itself meets NABH's expectation that hospitals run a risk management programme. |
| **ICH Q9(R1)** (pharma pack) | Severity → safety impact. Probability → likelihood. **Detectability** → credit for detective controls in control effectiveness. Q9(R1)'s point about reducing subjectivity is why rules decide and confidence is shown. Formality scales with risk: the review gates bite harder on CRITICAL. |
| **ISO 27001 / DPDP Act** (data pack) | ISO 27001 clause 6.1.2 asks for consistent, valid, comparable assessments and set acceptance criteria. A versioned rulebook plus client appetite meets that. Annex A controls feed the control inventory. DPDP penalties (up to ₹250 crore for security-safeguard failures) seed regulatory impact = 5. Data-principal volume and children's data feed exposure. |

## 4. Risk model

### 4.1 Identification and grouping

- **Exposures.** Every requirement whose company scope is APPLICABLE or CONDITIONAL (NOT_APPLICABLE excluded) becomes an **exposure**: "failure to meet requirement R at site S".
- **Theme assignment** is deterministic, from rulebook data:
  - regulator → theme
  - regulation title pattern → theme
  - NABH chapter → theme
  - taxonomy tag → theme
  - An exposure that matches nothing goes to `Unthemed — <regulation>`, and gate 3 opens a task to classify it. **The LLM does not classify themes.**
- **Risk** = group of exposures with the same **(theme, site)**. Site-independent duties (company-level) use site = `*`.
- **Roll-up.**
  - Risk inherent = **max** over its exposures. Risk residual = **max** over its exposures.
  - The exposure that drives the result is named in the derivation.
  - This is conservative on purpose: grouping never hides a bad member.

### 4.2 Impact (per exposure)

- There are five dimensions, each scored 1–5 by first-match rules:
  - regulatory / legal
  - safety (patient / product / worker / public)
  - operational continuity
  - financial
  - reputational
- **Aggregate = max** (the worst credible consequence). Averaging would hide a 5.
- **Regulatory** comes from `penalty_provisions` (own, else inherited from the enabling Act) and from licensing consequences.
  - When no clause is found, the default is set by instrument type, with a confidence penalty.
- **Safety** comes from the theme's safety class and the NABH category floor.
- **Operational** comes from licence dependence: the duty guards a licence the site operates on.
- **Financial** compares the maximum fine with turnover.
- **Reputational** depends on whether the regulator publishes enforcement, or there is a risk of losing accreditation.

### 4.3 Likelihood (theme × site, before controls)

- **Base** = inspection / enforcement frequency per regulator, from the sector pack: continuous 4, annual 3, biennial 2, rare 1.
- **Modifiers** (summed, then clamped to 1–5):
  - exposure (site count, pack-defined scale index such as beds ≥ 200)
  - history on the theme: open observations, repeat observations, warning letters, penalties, overdue CAPAs, and a clean inspection with attestation, which counts −1
  - change velocity (see §2.10)
- **Mandatory inputs:** history (records or attestation), site count and the sector's scale metric.

### 4.4 Control effectiveness

- **Grade per (control, requirement):**
  - **TESTED:** an approved document plus test or audit evidence
  - **DOCUMENTED:** an approved document
  - **CLAIMED:** self-declared only
  - **ABSENT:** confirmed nothing
  - **UNKNOWN:** not known yet
- **Capped by the requirement's gap status:** GAP / NOT_COVERED → ABSENT; PARTIAL → at most DOCUMENTED.
- **Freshness decay.** Age of the newest evidence ÷ the control's expected interval: above 1.5× drops one grade, above 3× drops two.
- **Exposure grade** = the best grade among the controls mapped to that requirement.

### 4.5 Residual

- **Effect on likelihood:** TESTED −2, DOCUMENTED −1, CLAIMED 0, ABSENT 0.
- **Effect on impact:** −1 only when a **corrective** control is TESTED (business continuity plan, recall procedure, incident response).
- Floors at 1. Total reduction is capped at likelihood −2 and impact −1.
- The residual band comes from the same matrix.

### 4.6 Confidence (shown separately, never mixed into the score)

- Start at 100 and subtract:
  - each default used: 10 (at most 40)
  - each unconfirmed extracted fact: 5 (at most 25)
  - gap status still LLM-unreviewed: 10
  - applicability CONDITIONAL: 15
  - evidence CLAIMED only: 15
  - uncalibrated sector pack: 10
- Bands: High ≥ 75, Medium ≥ 50, Low below 50.

### 4.7 Missing inputs and bounds

- **Mandatory input missing** → INSUFFICIENT_EVIDENCE, with the list of what is missing.
- **Bounds.** The engine still computes a **best / worst range**, by putting each missing factor at its minimum and its maximum. The range is shown greyed, never as a score.
- **Gap list ranking.** For each missing input: the number of risks whose worst case would exceed appetite, then the sum of their worst-case scores. That figure is "how much risk it's hiding".
- **Optional input missing** → the rulebook default (neutral to pessimistic) is used, with a confidence penalty, and it is listed.

### 4.8 Evaluation (first match wins)

| # | Condition | Verdict |
|---|---|---|
| EV-01 | applicability unresolved, or interpretation flagged ambiguous | REVIEW_REQUIRED |
| EV-02 | a mandatory input is missing | INSUFFICIENT_EVIDENCE |
| EV-03 | the client's appetite is not yet approved | REVIEW_REQUIRED (scores still shown) |
| EV-04 | residual band above tolerance, or a zero-tolerance category breached | ESCALATE |
| EV-05 | residual band above appetite | TREAT |
| EV-06 | confidence below the client's threshold | REVIEW_REQUIRED |
| EV-07 | — | WITHIN_APPETITE |

- **INSUFFICIENT_EVIDENCE** = data is missing, and the client can fix it.
- **REVIEW_REQUIRED** = data is present, but a person must judge.

### 4.9 Worked trace (illustrative numbers, before any build)

**Risk:** "Biomedical waste segregation & disposal — Hyderabad site". The worst exposure is a BMW Rules 2016 segregation duty.

- **Impact:**
  - regulatory 5 (REG-IMP-01: imprisonment under the enabling EP Act)
  - safety 4 (theme BMW = major)
  - operational 5 (OPS-IMP-01: guards the SPCB authorisation)
  - financial 2
  - reputational 2
  - **Impact = 5.**
- **Likelihood:** base SPCB annual = 3; beds 250 → +1 (LIK-EXP-02); history attested none = 0; no wording change = 0. **Likelihood = 4.**
- **Inherent:** I5 × L4 → **CRITICAL** (product 20).
- **Controls:**
  - Segregation SOP v3: approved, so DOCUMENTED.
  - Monthly bin-audit log: newest entry is 70 days old against an expected 45, so 1.56× → it drops from TESTED to DOCUMENTED.
  - Gap status PARTIAL caps the grade at DOCUMENTED anyway.
- **Residual:** L 4 → 3, I 5 → **CRITICAL**.
- **Evaluation:** safety appetite MEDIUM, tolerance HIGH, so CRITICAL > tolerance → **ESCALATE**.
- **Confidence:** 100 − 10 (gap status unreviewed) − 10 (beds and SOP approval unconfirmed) = 80, **High**.
- **Ripple example:** a fresh bin audit is uploaded → TESTED → L 2 → I5 × L2 = HIGH → **TREAT**. The diff shows "LIK −1: CTRL bin-audit evidence 2026-11-10 (TESTED)".

## 5. Rulebook as data (excerpt)

- Rulebooks are YAML files, versioned with semver.
- Each one is validated against a JSON Schema and pinned by content hash on every assessment.
- Conditions compile to structured predicates (`{path, op, value}`). There is no `eval` and no free code.
- Packs `extend` the base.

```yaml
rulebook: base
version: 1.0.0
status: draft                 # draft → published (gate 8) → retired
bands: [LOW, MEDIUM, HIGH, CRITICAL]
matrix:                       # rows impact 5→1 · columns likelihood 1→5
  5: [HIGH,   HIGH,   CRITICAL, CRITICAL, CRITICAL]
  4: [MEDIUM, HIGH,   HIGH,     CRITICAL, CRITICAL]
  3: [LOW,    MEDIUM, MEDIUM,   HIGH,     HIGH]
  2: [LOW,    LOW,    MEDIUM,   MEDIUM,   HIGH]
  1: [LOW,    LOW,    LOW,      MEDIUM,   MEDIUM]

impact:
  aggregate: max
  dimensions:
    regulatory:
      mandatory: true
      rules:                  # first match wins
        - {id: REG-IMP-01, when: {penalty.imprisonment: true}, score: 5}
        - {id: REG-IMP-02, when: {consequence.any_of: [licence_cancellation, licence_suspension, accreditation_withdrawal]}, score: 5}
        - {id: REG-IMP-03, when: {penalty.max_fine_inr: {gte: 10000000}}, score: 4}   # ≥ ₹1 crore
        - {id: REG-IMP-04, when: {penalty.max_fine_inr: {gte: 1000000}}, score: 3}    # ≥ ₹10 lakh
        - {id: REG-IMP-05, when: {penalty.present: true}, score: 2}
      default: {by_instrument_type: {act: 3, rules: 3, regulation: 3, standard: 2, guideline: 1}, confidence_penalty: 10}
    safety:
      mandatory_in_packs: [healthcare, pharma, food, manufacturing]
      rules:
        - {id: SAF-IMP-01, when: {theme.safety_class: catastrophic}, score: 5}
        - {id: SAF-IMP-02, when: {theme.safety_class: major}, score: 4}
        - {id: SAF-IMP-03, when: {theme.safety_class: moderate}, score: 3}
        - {id: SAF-IMP-04, when: {theme.safety_class: minor}, score: 2}
      not_applicable_when: {theme.safety_class: none}
    operational:
      rules:
        - {id: OPS-IMP-01, when: {exposure.guards_licence: true}, score: 5}
        - {id: OPS-IMP-02, when: {theme.critical_process: true}, score: 4}
      default: {score: 2}
    financial:
      rules:
        - {id: FIN-IMP-01, when: {ratio: {num: penalty.max_fine_inr, den: profile.turnover_inr, gte: 0.01}}, score: 4}
        - {id: FIN-IMP-02, when: {ratio: {num: penalty.max_fine_inr, den: profile.turnover_inr, gte: 0.001}}, score: 3}
      default: {score: 2, confidence_penalty_if_missing: [profile.turnover_inr]}
    reputational:
      rules:
        - {id: REP-IMP-01, when: {regulator.publishes_enforcement: true}, score: 4}
        - {id: REP-IMP-02, when: {consequence.any_of: [accreditation_withdrawal]}, score: 4}
      default: {score: 2}

likelihood:
  base: {from: regulator.inspection_frequency, map: {continuous: 4, annual: 3, biennial: 2, rare: 1}}
  modifiers:                  # summed, then clamped 1..5
    - {id: LIK-EXP-01, when: {exposure.sites: {gte: 3}}, add: 1}
    - {id: LIK-EXP-02, when: {exposure.scale_index: high}, add: 1}
    - {id: LIK-HIS-01, when: {history.open_observations_theme_24m: {gte: 1}}, add: 1}
    - {id: LIK-HIS-02, when: {history.any_of_36m: [repeat_observation, warning_letter, penalty, licence_action]}, add: 2}
    - {id: LIK-HIS-03, when: {history.overdue_capa_theme: {gte: 1}}, add: 1}
    - {id: LIK-HIS-04, when: {history.clean_inspection_theme_24m: true}, add: -1}
    - {id: LIK-CHG-01, when: {requirement.section_changed_12m: true, evidence.predates_change: true}, add: 1}
  mandatory: [history.records_or_attestation, exposure.sites, exposure.scale_metric]

controls:
  grades: [UNKNOWN, ABSENT, CLAIMED, DOCUMENTED, TESTED]
  cap_by_gap_status: {GAP: ABSENT, NOT_COVERED: ABSENT, PARTIAL: DOCUMENTED}
  freshness: [{over: 1.5, drop: 1}, {over: 3.0, drop: 2}]
  expected_interval_days: {continuous: 30, monthly: 45, quarterly: 120, half_yearly: 210, annual: 400}
  residual_effect:
    TESTED:     {likelihood: -2, impact_if_corrective: -1}
    DOCUMENTED: {likelihood: -1}
    CLAIMED:    {likelihood: 0}
    ABSENT:     {likelihood: 0}
  max_reduction: {likelihood: 2, impact: 1}
  unknown_is_missing: true    # UNKNOWN → mandatory input missing → INSUFFICIENT_EVIDENCE

grouping: {key: [theme, site], rollup: {inherent: max, residual: max}, fallback_theme: "Unthemed — {regulation}"}

confidence:
  start: 100
  penalties: {default_used: [10, 40], fact_unconfirmed: [5, 25], gap_status_unreviewed: 10,
              applicability_conditional: 15, evidence_claimed_only: 15, pack_uncalibrated: 10}
  bands: {HIGH: 75, MEDIUM: 50}

evaluation: [EV-01, EV-02, EV-03, EV-04, EV-05, EV-06, EV-07]   # §4.8, as data
```

## 6. Intake specification

- **Order of sources:** public record → connectors → documents (rules, then the LLM with a citation; the client confirms) → manual gap-fill last.
- **Citations.** Every extracted fact is stored as PROPOSED with file, **page**, section and a quote. Page capture is new.

### (a) Organisation profile and exposure

| Field | Feeds | Source | If missing |
|---|---|---|---|
| Entity type, legal form | Identification (applicability) | Public record, documents | No exposures → REVIEW_REQUIRED |
| Sectors / sub-sectors | Sector pack choice | Documents → manual | Base rulebook only, pack_uncalibrated penalty |
| Jurisdictions (states) | Identification | Licences, addresses → manual (fix the hard-coded India) | REVIEW_REQUIRED |
| **Sites:** address, type, state | Likelihood (exposure), grouping by site | Licences, documents → confirm | **INSUFFICIENT_EVIDENCE** (mandatory) |
| **Scale metric per site** (hospital: beds, IPD/OPD a year, OTs; pharma: batches a year, products, markets; finance: customers, AUM; factory: workers, hazardous processes) | Likelihood (scale index), thresholds | Licence documents (bed count) → manual | **INSUFFICIENT_EVIDENCE** (mandatory) |
| High-risk service lines (X-ray / CT, blood bank, NICU, dialysis, pharmacy, transplant; sterile, controlled drugs) | Safety impact, theme activation | Licences (AERB, blood bank) → manual | Theme maximum used (pessimistic), confidence − |
| **Licences as records:** number, issuer, site, valid until, conditions | Operational impact (guards_licence), likelihood | Licence documents → confirm | Operational impact defaults to 4, REVIEW flag |
| Turnover | Financial impact ratio | Public record → manual | Absolute bands, confidence − |
| Employees, headcount by department | Labour-theme exposure | Profile, organisation chart | Optional, default |
| Personal data: categories, volume of data principals, children's data | Data-pack impact and exposure | Data-assets section → manual | Data risks INSUFFICIENT_EVIDENCE |
| Critical outsourced services (waste agency, lab, catering) | Likelihood (third-party) | Contracts → manual | Optional |

### (b) Control inventory and evidence

| Field | Feeds | Source | If missing |
|---|---|---|---|
| Controls: name, type (preventive / detective / corrective), frequency, owner | Control grade, residual | Document classification and import → confirm | UNKNOWN → INSUFFICIENT_EVIDENCE |
| Control ↔ requirement mapping | Which exposures a control reduces | Gap `covered_by` plus LLM proposal with citation → reviewer confirms | UNKNOWN |
| Policy / SOP: version, effective date, approver | DOCUMENTED | Document intake (exists) | At most CLAIMED |
| Test / audit evidence, with date (audit reports, logs, registers, calibration, mock drills, training records) | TESTED, freshness | Document intake by type and date → confirm | At most DOCUMENTED |
| Expected interval per control | Freshness decay | Control frequency, else rulebook default | Default used |
| Self-declarations ("we do X") | CLAIMED (gate 4) | Questionnaire | — |

### (c) History (36 months)

| Field | Feeds | Source | If missing |

## 8. Data model (tenant schema; every table added to `tenancy.COMPANY_TABLES`)

- **Bitemporal columns** on assessments, ratings, appetite and overrides:
  - `valid_from` / `valid_to` = true in the world
  - `recorded_at` / `superseded_at` = known to us
- Rows are append-only. A correction inserts a new row and sets `superseded_at` on the old one.
- "Position on date X, as we knew it on date K":
  `valid_from ≤ X < coalesce(valid_to, ∞) AND recorded_at ≤ K AND (superseded_at IS NULL OR superseded_at > K)`

## 9. Cascade integration and ripple

- **Computed risk nodes** show inherent band/score, residual band/score, a verdict chip and a confidence pill.
  - INSUFFICIENT_EVIDENCE shows a hatched pattern and the best–worst range.
- **Events that queue a recompute** (only the affected risks, found through `risk_factor_values` / `risk_exposures`):
  - regulation `section_changes`
  - requirement applicability changes
  - gap status changes
  - control or evidence writes
  - fact confirmation
  - history records and attestations
  - overrides
  - appetite changes (re-evaluate verdicts only)
  - rulebook publish (full recompute, dry-run first; gate 8)
- **Idempotent.** The engine hashes inputs + rulebook. When nothing changed, no new version is written.
- **Diff.** When something changed, the new version stores before → after for inherent, residual, verdict and confidence, plus the driving factors and the event that caused each.
- **Execution.** A timer job like the watcher, plus synchronous recompute for a single-risk action in the UI.
- **Derivation panel** (click a risk node or a register row; precedent `ImpactPanelTab`):
  - exposures
  - factors with value, source chip (rule / extracted / entered / default) and citation
  - rules fired, rulebook version + hash
  - control grades with freshness
  - missing inputs and bounds
  - review history, overrides and treatment
  - an "as of" date picker (bitemporal)

## 12. Assumptions and judgment calls

1. Grouping by (theme, site), with max roll-up for inherent and residual.
2. Band from a lookup matrix, not product thresholds.
3. Impact aggregate = max.
4. Likelihood is theme × site level; impact and control grade are exposure level.
5. Residual effects: TESTED −2 / DOCUMENTED −1 likelihood; corrective TESTED −1 impact; total caps.
6. Freshness at 1.5× and 3× the expected interval.
7. History attestation is mandatory, so day 1 is mostly INSUFFICIENT_EVIDENCE.
8. LLM gap status = a proposed fact (cap + confidence penalty); `rk` unused.
9. Penalty inheritance through `enabling_act`, plus a new licensing-consequence regex.
10. Inspection frequencies are seed values. The healthcare pack is calibrated; other packs are flagged uncalibrated.
11. Upstream stays non-temporal; assessments snapshot their inputs.
12. No per-client rulebook tuning in v1. Clients tune only through appetite, which keeps clients comparable.
13. The treatment options are the brief's four. ISO 31000 also lists **avoid**; I'd add it.
14. The LLM may write rationales only from the derivation JSON. A deterministic check verifies every number and band it mentions; a mismatch is rejected and the template text is used.
15. The new `leadership` role holds `govern`.
16. A lower override needs four eyes. An override goes STALE when its inputs change.

## 14. Addendum v0.2 — decisions of 12 Nov 2026, and the risk-identification skeleton

### 14.1 Decided

- **D1 · Scope.**
  - The risk universe is the **union of every identification path** in §14.3.
  - The sample register (`Risk_Register_CAPA_Comprehensive_Anonymized.xlsx`, 131 risks) becomes **risk library v1**.
  - Its ratings are benchmarks only. Its own notes call them illustrative.
  - Template applicability is **inclusive**: an unknown fact makes the template a candidate for review. It never drops it silently.
- **D2 · Client risk criteria.**
  - Client leadership sets the band matrix and band labels at **G1**, together with appetite. The default is the rulebook matrix.
  - The 1–5 impact and likelihood scores stay rule-driven.
  - This replaces judgment call #12 for the band mapping only.
  - When a client's matrix conflicts with its own range key, G1 shows the conflict and leadership picks. The sample has such a conflict: cell L2 × I5 is H in the matrix but M in the 4–10 range key.
- **D3 · Treatment vocabulary (ISO 31000 meanings).**
  - **ACCEPT** = retain by informed decision, no further action.
  - **AVOID** = stop, or don't start, the activity.
  - **MITIGATE** = reduce likelihood or impact.
  - **TRANSFER** = share it (insurance, contract).
  - **ESCALATE** = refer it upward.
  - The sample legend's Table 7 has Accepted and Avoidance **interchanged**. The library uses the corrected meanings.
  - On import, a row labelled Avoidance whose post-treatment rating equals its prior rating is **flagged for review**, not reinterpreted. There are 5 such rows in the sample.
- **D4 · Target risk.**
  - Target is a third assessment point: inherent → residual → **target**.
  - The engine projects target = residual recomputed as if each planned action's control reached TESTED with fresh evidence.
  - The owner's treatment decision (G6) links the actions the projection uses.
- **§13 defaults stand** (sign-off without changes):
  - (theme, site) grouping for obligation risks
  - history attestation mandatory
  - a leadership role holding `govern`
  - four-eyes for lowering overrides
  - the healthcare pack first
  - AVOID added
  - 4 bands, with labels client-configurable under D2
- **Sample register semantics on import.**
  - "Prior to Risk Treatment" is a rating *with existing controls* (its likelihood scale describes control strength), so it is compared with our **residual**.
  - "Post Risk Treatment" is compared with our **target**.
  - Neither sets a score.
  - Row 54, where risk rises after treatment, and the 3 Mitigation rows with no change are flagged on import.

### 14.2 Library templates bind to graph node types, not sectors

Each template carries:

- id, title, `node_type`, and an `applies_when` predicate on graph facts
- theme, CIA, risk_type
- impact seeds per dimension, and a base likelihood class
- typical controls, each with an expected interval and an evidence type (from the "Risk Mitigation Actions" column)
- typical mitigation actions
- linked obligation themes, used to merge with Path A
- the benchmark rating
- its source: the sample register, a sector pack, or a promoted custom risk

| Sample group (count) | Binds to | Applies when |
|---|---|---|
| IT, cyber, SDLC (52) | System; activity "builds software" | Systems exist; cloud-hosted; internet-facing; AI in use; develops software |
| HR (11) | Organisation, Role | Employees > 0; remote work allowed |
| Finance (8) | Organisation | Always |
| Legal and compliance (8) | Organisation, Third party | Always; imports/exports for sanctions |
| Privacy (4) | Data asset | Personal data held; residency outside India for cross-border |
| Third party, procurement, supply chain (8) | Third party, Product | Vendors exist; physical goods |
| Continuity, facilities, health & safety (8) | Site, Process | Per site; critical processes |
| Enterprise risk, ESG (8) | Organisation | Listed or large, for ESG reporting |
| Sales, marketing, customer service (8) | Organisation | Customer-facing marketing |
| Operations, engineering, product, projects, administration (16) | Process, Product | Per critical process or product |

**Sector packs become thin.** They add sector node subtypes and attributes (hospital service lines, pharma products and batches, bank products), theme mappings and extra templates. **They extend coverage; they never cap it.**

**Intake gap.** There is no third-party / vendor section today. Add one: name, service, criticality, data shared, contract, alternatives.

### 14.3 Five identification lenses (coverage = their union)

1. **Obligations** (Path A). Every applicable requirement becomes an exposure (§4.1).
2. **Library templates** (Path B). A template × every matching graph node becomes an exposure. Group key = (template, site).
3. **Coverage check.** A critical node (process, system, data asset, third party, site, licence) with no analysed risk is a **coverage gap**. It goes on the gap list and is never given a score.
4. **Events.** Incidents, observations, complaints, near misses, CAPAs, regulator action against peers (enforcement watch) and new regulations (watcher). An event that maps to no existing risk opens an **emerging-risk candidate**.
5. **People and imports.**
   - Manual proposals.
   - Workshop checklists per function: the library risks for that function, plus its processes that have no risk.
   - Rows in the client's own register that we did not produce.

### 14.4 New gate G9 · Candidate triage

| Trigger | Who | Can do | Logged |
|---|---|---|---|
| A candidate from lenses 3–5, or a template whose applicability is unknown | Compliance manager (+ function head) | Accept, choosing a template or theme; merge into an existing risk; create a custom risk; dismiss with a reason | Decision, reason, source lens and event |

- For a custom risk, the human picks the classification (theme, impact basis). That is an input, and the rules compute the score.
- Until an impact basis exists, the verdict is INSUFFICIENT_EVIDENCE.

### 14.5 Learning loop

1. Accepted custom risks become proposed library templates: structure only, anonymised, opt-in per client.
2. A platform curator reviews them.
3. They are published in the next **library version**, versioned and dry-run like the rulebook (G8).
4. Every organisation whose graph matches then gets the new candidate.

### 14.6 Completeness metrics (board view)

- Share of critical nodes with an analysed risk
- Share of applicable obligations mapped to a risk
- Open orphan events
- Register review age

**Changes from the design, found while building**

1. **`applies_to` on rules.** A rule can name the exposure kinds it runs for (obligation, template, event).
   - Without it, a penalty fact is "unknown" for every library template, and a graph node's criticality is "unknown" for every obligation.
   - Unknowns are taken at their worse value, so every score would have been pushed to 5.
2. **`assumed: true` on defaults.** Only a default that is an assumption costs confidence: regulatory by instrument type, safety without a theme, the likelihood base.
   - A baseline default reached because every rule was checked and none holds is an answer, not a gap.
3. **New confidence penalty `mandatory_missing`** (25 per input, capped at 60). An INSUFFICIENT_EVIDENCE score can never read "High confidence".
4. **Themes default to `safety_class: none`, `critical_process: false`.** A theme that says nothing means "no", never "unknown".
5. **No new licensing extractor.** `penalties.py` already classifies "cancel / suspend the registration" as SUSPENSION_CANCELLATION. The input assembler (Phase 2/4) maps that to `consequence: licence_suspension`.
6. **The rulebook is validated in code**, not by JSON Schema, so no new dependency. PyYAML is added to requirements.txt; the server venv already has it through langchain.
7. **Input contract for the assembler.** Facts the rules read must be set explicitly, including false and 0 (`exposure.guards_licence`, `requirement.section_changed_12m`, `penalty.max_fine_inr: 0` when no fine is stated). A fact left out is unknown and priced at its worse value.

- Tabs: To decide (the queue, by kind of decision, "For me"), Register, Questions, Rulebook. A risk opens in a panel: where it stands, owner, treatment, overrides, controls, what it covers, history.
- Notifications link to `/risk-review?task=<id>`, which opens that task's risk.
- API layer: `src/services/riskReviewApi.ts`. Task reasons are stored with a structured `detail` and worded on screen in each language.

**Decisions taken while building**

1. **Lens 1 (obligation risks) moves to Phase 4.** Assembling requirement × site exposures needs penalties, gap status and applicability per requirement — the same reads as the dependency index. The tables and gates already take them (G3 is exercised through template exposures).
2. **Organisation and site nodes are not graded for criticality** (`criticality: n/a`). Left unknown, OPS-IMP-03/04 priced every organisation template at operational 5. Third parties, systems and processes keep their real criticality; unknown is still priced at the worst.
3. **A node type with nothing listed gets one "none listed yet" node**, so its templates stay in the register (D1) at the precautionary score until the list exists.
4. **The questions (G9 in bulk).** Twelve organisation facts decide most templates ("do you build software?"). One answer settles every candidate that waits on it; a person's dismissal is never undone by a re-run unless a new undecided node appears.
5. **Controls are recorded per risk** (the template's typical controls, or one a person names). A reviewer may record only CLAIMED or ABSENT; DOCUMENTED and TESTED need a compliance manager and evidence with its date. A claim on a HIGH or CRITICAL risk opens G4 for someone else to validate.
6. **Idempotence ignores the date.** The engine's own hash includes `as_of`; the register keys on inputs + appetite + rulebook, and also writes a new version when the outcome changes (evidence decays with time).
7. **A provisional worst case is not routed to G5.** INSUFFICIENT_EVIDENCE already says it; routing it flooded the queue (40 of 129 risks on a first run).
8. **G5 acknowledgement is final per assessment version**; G6 opens again when an acceptance expires.
9. **A base-pack company has no size thresholds**, so `exposure.scale_index` is `low` (size adds nothing) rather than missing. Follow-up: a sector-agnostic scale index (employees) in `base.yaml`.
10. **Mitigation actions** are created in the existing actions table as Proposed and moved to Open by the decider (source `risk-treatment`), so the engine-only-proposes rule stands. Their kind (preventive / corrective) feeds the target (D4).

### Phase 3 follow-up — controls in bulk (13 Nov 2026, local; not deployed)

A first register stalled on "can't score yet": 102 of 113 risks waited on their controls, entered one at a time.

| Path | What |
|---|---|
| `regulatory_ingestion/risk/controls_import.py` | Matches the company's own controls (the `controls` library with tests and evidence links, and controls imported as company records) to each risk's unknown typical controls; the control workbook (download prefilled, upload .xlsx or .csv, check every row, apply the rows that pass); coverage. |
| `regulatory_ingestion/api_risk.py` | `GET /controls/matches`, `POST /controls/matches/apply`, `GET /controls/workbook`, `POST /controls/import` (check, or apply). `/register` now reports how many risks wait on controls. |
| `tests/test_risk_controls_import.py` | 15 tests. 123 risk tests in all. |
| App | A **Controls** tab in Risk review (matches with checkboxes; the workbook in three steps with a row-by-row check), and a callout on the queue and register while risks wait on controls. |

**Rules**

1. **Matching is deterministic:** the words two controls share, weighted by how rare they are, with register shorthand expanded (VA, PT, DR, MFA, KYC …). A match is a proposal; nothing is written until a person chooses it.
2. **A record never earns a grade beyond its evidence:** a passed test → TESTED; effective with a test date and linked evidence → TESTED; evidence on file → DOCUMENTED; a failed test or "ineffective" → ABSENT; anything else → CLAIMED (which opens G4 on a high risk).
3. **Both paths write through `review.record_control`,** so the role rules hold row by row (a reviewer: self-declared or absent only; documented and tested need a compliance manager, evidence and its date; no future dates). Each rating keeps its `source` (person, workbook, control:<id>, entity:<id>).
4. **A month alone ("Jun 2026") is read as its first day,** the older side for evidence decay.
5. **Re-uploading the same workbook writes nothing:** unchanged rows are reported as unchanged.
6. **openpyxl** is now pinned in requirements (production code already imported it for remediation exports and document intake).

**Decisions taken while building**

1. **One risk per theme for the whole organisation.** The design's (theme, site) grouping needs per-site applicability, which requirements do not carry yet (scopes are UNASSESSED). Follow-up: split by site once geography scopes are evaluated.
2. **Penalty = the regulation's highest stated ceiling.** `penalty_provisions` records where a penalty is written (often a schedule or an offences section), not which duty it punishes, so every duty of a regulation carries its ceiling. Rules with no penalty clause inherit the Act named in `enabling_act`. Follow-up: map schedule items to the sections they punish.
3. **A duty's applicability stays on the Requirements page.** Requirement-level REVIEW_REQUIRED / UNASSESSED duties are listed as pending (unscored, costing confidence); the register opens no task for them, so the two screens never disagree.
4. **A regulation without a theme is not scored.** Its duties sit in "Obligations without a theme yet" (verdict REVIEW_REQUIRED, not a precautionary CRITICAL) with one G3 task per regulation; the person's choice wins over the mapping on the next run.
5. **Controls count only when a person accepted the mapping** (`control_requirements.review_status` ACCEPTED / APPROVED), graded no better than their own evidence (same rule as the control import). The gap review's status caps or implies the grade, unreviewed.
6. **`regulator.publishes_enforcement` is set only when the enforcement table has rows**; with none on file it stays unknown and is priced at its worse value.
